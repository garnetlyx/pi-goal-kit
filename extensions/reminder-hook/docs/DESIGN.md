# Reminder Hook

A non-blocking "park and resume" mechanism. When the agent has to wait — for
market open, a download, a build, CI/CD, a URL to become healthy, a log line
to appear, a process to exit, or any other completable condition — it calls
`set_reminder` with a shell predicate and stops. When the condition is met,
the extension injects the agent's own resume prompt back into the session and
posts a system notification. The conversation is never blocked.

## How it works

```
agent calls set_reminder { condition, message, ... }
        │
        ▼
extension arms a setInterval (polled every poll_seconds)
        │
        │  bash -c "$condition" exits 0   (powershell -NoProfile -Command on Windows without bash)
        ▼
pi.sendUserMessage(message, { deliverAs: "followUp" })
  + ctx.ui.notify + system notification (osascript / OSC777 / notify-send)
  + remove from reminders.json
```

The `followUp` delivery mode is what guarantees non-blocking behavior: if the
user is mid-conversation when the reminder fires, the resume message queues
and triggers a new turn only when the agent is idle. It never interrupts.

## Tools

| Tool | Fires when | Key params |
|------|------------|------------|
| `set_reminder` | condition exits 0 and/or time gate passes | `condition`, `at`, `in_minutes`, `poll_seconds`, `timeout_minutes`, `label` |
| `cancel_reminder` | manual cancel | `id` |

`set_reminder` parameters (all optional except `message`, but at least one of
`condition` / `at` / `in_minutes` is required):

- `message` — resume prompt the agent leaves for itself
- `condition` — a shell predicate; exit 0 = done. Runs under `bash -c` on macOS/Linux and on Windows when bash is present (Git Bash/WSL); otherwise under `powershell -NoProfile -Command`. The `set_reminder` response reports the active shell.
- `at` — `"9:30"`, `"09:30:00"`, ISO datetime; time gate
- `in_minutes` — countdown gate
- `poll_seconds` — poll interval (default 30)
- `timeout_minutes` — hard cap; fires flagged as timeout
- `label` — display label

Semantics:
- `at` / `in_minutes` only → fires once at that time
- `condition` only → polls immediately until true
- both → waits until the time, then starts polling

## Commands

- `/reminders` — list pending in a bordered, opaque focused overlay; `esc`, `q`, or `enter` closes it
- `/cancel-reminder <id>`

## Persistence and reload

Reminders are stored per session under
`state/agent/reminder-hook/sessions/<sessionId>/reminders.json`. On
`session_start` the extension clears any legacy persistent reminder widget and
re-arms every pending reminder. Pure-time reminders already due fire
immediately on the next start. Timers are cleaned up on `session_shutdown`.

## Why one generic tool

Every "wait for X" reduces to a shell predicate. Time, PIDs, files, URLs,
logs, market state, queue depth, CI status — all expressible as a shell
command with exit code 0. Letting the agent write the predicate covers any
future scenario without the extension growing new tool types. See the skill
for concrete predicate examples per scenario.

## Shell selection on Windows

Windows has no `bash` by default, so the condition executor is platform-aware:
on macOS/Linux it always uses `bash -c`. On Windows it probes for bash once
per process (Git Bash and WSL both provide one) and prefers it when found,
falling back to `powershell -NoProfile -Command`. The resolved shell is cached
and reported in the `set_reminder` response (`shell bash` / `shell powershell`)
so the agent writes the predicate in the matching dialect.
